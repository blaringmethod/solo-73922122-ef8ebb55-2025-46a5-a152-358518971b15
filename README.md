# 质检影像缺帧核对 API

质检影像缺档时，用于判断缺档该找**采集端**补登记，还是找**影像库**补归档的核对服务。
FastAPI + SQLite，全部以**闭区间号段**为单位存储与计算，帧号可跨十亿且不逐帧展开。

## 业务模型

- **批次**：登记每批影像应有的帧号范围 `[frame_start, frame_end]`，首尾包含。
- **清单**：采集端（`collector`）与影像库（`library`）各凭全局唯一的清单号，
  对一个**连续号段**做三种操作：
  - 登记（POST `/manifests`）
  - 更正（PUT `/manifests/{manifest_no}`），只允许改号段，批次/侧别不变
  - 撤回（POST `/manifests/withdraw`），撤回后同侧其他清单覆盖的帧仍算有记录
- **核对**（GET `/batches/{id}/reconcile`）返回四类**最大连续段**：
  `both_present`（双方齐全）、`only_collector`（仅采集端有 → 找影像库补归档）、
  `only_library`（仅影像库有 → 找采集端补登记）、`neither_present`（双方皆缺）。
- **按帧追查**（GET `/batches/{id}/frames/{frame_no}`）：返回该帧状态及两侧命中的清单号。

判定口径：`only_collector` 说明采集端已登记、影像库缺档 → 找影像库补归档；
`only_library` 相反 → 找采集端补登记；`neither_present` 两侧都要补。

## 关键设计

| 需求 | 实现 |
| --- | --- |
| 帧号跨十亿、不逐帧展开 | 帧号以 64 位整数存号段（`seg_start/seg_end` 闭区间），算法复杂度只与号段数有关 |
| 改撤读写量只随相交数据增长 | `coverage` 表是**引用计数步进段**：每段记录被几张有效清单覆盖；改撤 = 对号段 ±1，只读写与该号段相交的段及必要的并段边界，无关清单（无论连成一片还是排在前面）一行都不读 |
| 清单移到远处跳过中间记录 | 更正 = 旧号段 -1、新号段 +1，两次独立的局部增量，两段之间的记录不进入读写窗口 |
| 撤回不影响同侧重叠清单 | 覆盖段按计数维护：撤回只把号段计数 -1，同侧其他清单覆盖的帧计数仍 >= 1，继续算有记录 |
| 清单与核对结果同时生效 | 每次写操作在单个 `BEGIN IMMEDIATE` 事务内同时更新清单表与覆盖段表，异常即回滚 |
| 越界/入库失败保留原状 | 越界在事务内先校验抛 422；任何错误回滚，已提交数据不变；帧号超 int64 在入参层拦截 |
| 最大连续段 | 核对时把步进段按相邻关系合并即得该侧最大连续覆盖段，再求四类段 |
| 旧库升级 | 启动时检测旧结构（`coverage` 无 `cnt` 列），在事务内按原清单重建覆盖段，升级后可直接核对和改撤 |

### 覆盖步进段（本次修复的核心）

`coverage` 表同一 `(batch_id, side)` 下存互不重叠的号段，`cnt` 为该段被多少张
有效清单覆盖（>= 1）；相邻段 `cnt` 必不同（相同即已合并），段数 <= 2×清单数+1。

一次改撤的代价：

1. **索引定位**：常数次主键点查（含 `start` 的段、`start` 前一段、`end` 后一段），O(log n)；
2. **窗口读写**：只读出与号段相交的段及左右并段边界，扫描线在窗口内推进，
   完成切分、±1、删零计数段、合并同计数相邻段，写回时只写发生变化的行。

因此读写量 = O(与号段相交的段数 + 并段边界数)，与批次内无关清单总数无关。

### 三张表

- `batches`：批次号 + 应有帧号范围
- `manifests`：清单号、批次、侧别、状态（active/withdrawn）、号段
- `coverage`：按批次+侧别的引用计数步进段（随写操作增量维护）

号段运算见 `app/intervals.py`（合并 / 交集 / 差集，纯函数，零第三方依赖）。

## 启动方式

### Docker Compose（推荐）

```bash
docker compose up --build
# 服务： http://localhost:8000
# 文档： http://localhost:8000/docs   （Swagger UI，可直接演示改撤后的核对）
```

SQLite 数据文件在命名卷 `qc-data`（容器内 `/data/qc.db`），WAL模式。
旧版本的数据文件挂载进来后，首次启动自动升级覆盖段结构，原清单可直接核对/改撤。

### 本地直接运行

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

## API 一览

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/batches` | 登记批次应有帧号范围 |
| GET | `/batches/{batch_id}` | 查看批次 |
| POST | `/manifests` | 登记清单号段（自动越界校验） |
| PUT | `/manifests/{manifest_no}` | 更正号段（旧段 -1、新段 +1） |
| POST | `/manifests/withdraw` | 撤回清单（幂等冲突返回 409） |
| GET | `/manifests/{manifest_no}` | 查看清单 |
| GET | `/batches/{batch_id}/manifests` | 批次清单列表（可按 side 过滤） |
| GET | `/batches/{batch_id}/reconcile` | 四类最大连续段核对结果 |
| GET | `/batches/{batch_id}/frames/{frame_no}` | 按帧追查两侧清单号 |
| GET | `/health` | 健康检查 |

### 快速演示

```bash
python scripts/demo.py            # 默认打 http://127.0.0.1:8000，含改撤后核对的演示
pytest -q                         # 35 个测试
python scripts/bench.py           # 改撤读写量自测（新旧实现对比）
```

`/docs` 演示改撤后核对的点法：POST `/batches` 建批次 → POST `/manifests`
登记同侧连片清单与一张一帧清单 → POST `/manifests/withdraw` 撤回一帧清单 →
GET `/batches/{batch_id}/reconcile` 查看四类段（缺口精确到被撤回的那一帧）。

## 改撤读写量自测（scripts/bench.py 实测）

三种场景，批内无关清单从 1 万增至 10 万，统计单次改撤读写的表行数
（新实现另计常数次 O(log n) 索引定位）：

| 场景 | 批内清单数 | 旧实现读清单行数 | 旧耗时 ms | 新实现读行数 | 新实现写行数 | 新耗时 ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| A 撤回一帧(同侧连片) | 10,000 | 10,000 | 95.0 | 3 | 3 | 3.5 |
| A 撤回一帧(同侧连片) | 100,000 | 100,000 | 990.1 | 3 | 3 | 2.0 |
| B 撤回一帧(前面不相交) | 10,000 | 9,999 | 25.2 | 2 | 1 | 2.9 |
| B 撤回一帧(前面不相交) | 100,000 | 99,999 | 224.5 | 2 | 1 | 3.9 |
| C 更正移到远处 | 10,000 | 20,001 | 113.2 | 4 | 4 | 4.2 |
| C 更正移到远处 | 100,000 | 200,001 | 1,064.0 | 4 | 4 | 2.4 |

旧实现随批内清单数线性增长（撤回一张一帧清单也会扫过几乎整批）；
新实现在三种场景下读写均为常数，且清单移到远处时两段之间的记录不被读写。
测试机：本仓库开发容器（Python 3.11 / SQLite 3.40），耗时为单次测量值，仅作量级参考。

## 错误约定

- `404`：批次/清单不存在
- `409`：批次号/清单号重复、撤回已撤回清单、更正已撤回清单
- `422`：号段非法（起点大于终点）、越出批次范围、帧号超 64 位整数
- 所有写错误都在提交前拦截，库内状态保持调用前原状

## 已知限制 / 后续工作

- 按帧追查（`/frames/{frame_no}`）的清单命中查询仍是 B 树单边界区间扫描，
  极端情况下会读过该帧之前的部分清单行；它不在改撤路径上，本次未改。
- SQLite 单写者：写操作经 `BEGIN IMMEDIATE` 串行，足够单实例部署；
  多实例水平扩展需换客户端-服务端数据库，表结构与增量算法可直接平移。
- 旧库升级为启动时一次性全量重建覆盖段，超大旧库首次启动会有相应耗时。
